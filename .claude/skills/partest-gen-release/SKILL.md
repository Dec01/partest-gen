# Releasing partest-gen

## When to use this

The user explicitly asked to release, publish, or cut a version.

**Never bump `__version__` outside such a request.** A version bump is not part of a feature.

## Procedure

The authoritative checklist is `docs/wiki/howto/release.md` — follow it. This skill exists so
you load it at the right moment and do not skip the parts that are easy to forget.

## The parts that get skipped

1. **Judge the version by what it writes, not by what it exports.** A renamed or moved
   generated file breaks hand-written imports in every project that ran the previous version.
   That is a **major** bump, and so is any widening of the overwrite policy.
2. **Regenerate the wheel docs.** `python tools/docs_build_wheel.py`. `partest_gen/docs/` is
   generated from `docs/wiki/` pages marked `ships_in_wheel: true`. Hand-editing it, or
   forgetting to regenerate, is how internal notes reach PyPI.
3. **Generate a real tree and look at it.** The unit tests check emitters in isolation; only a
   full run shows what a user gets:
   ```bash
   partest-gen from-openapi /tmp/rel-check --file tests/fixtures/sample_openapi.yaml \
     --depth p1 --with-ui --force
   grep -rL "AUTO-GENERATED by partest-gen" /tmp/rel-check/src --include="*.py"
   ```
   The second command lists files the generator does not claim. An unexpected entry is a lost
   banner — a file that silently stops being refreshed in every project at once.
4. **Check the `partest` floor.** `install_requires` must name the version whose methodology
   this release emits against. A suite generated here has to be countable by that harness.
5. **One version source.** `partest_gen/__init__.py`; `setup.py` reads it. Do not add the
   number anywhere else.
6. **Update `docs/wiki/status.md`** — current version, the `partest` floor, and remove what
   just shipped from "what is next".
7. **Open the rendered PyPI page.** `twine check` passing does not mean the page reads well.

## Commands

```bash
python tools/docs_build_wheel.py           # regenerate first: the checks compare against it
python tools/check_all.py --strict-docs --package
git tag -a vX.Y.Z -m "partest-gen X.Y.Z — …"   # the tag is what publishes
git push origin master vX.Y.Z
```

`--strict-docs` makes a stale page fail rather than warn. Ordinary CI does not use it, because
a page going stale should not block ordinary work — but a release publishes those pages.

## Red lines

- **Ask before pushing the tag.** The tag starts the publishing workflow. Publishing is
  irreversible — PyPI never lets a version number be reused — so confirm the version and the
  artifact contents with the user first. The `pypi` environment also requires their review,
  but do not treat that as the place to think: get agreement before tagging.
- **Never handle a PyPI token.** Publishing uses trusted publishing, so no token exists. If
  someone offers one, decline, and tell them to revoke it if it was sent in a message.
- Push the release commit and tag to GitHub as well; PyPI carries the artifact, the repository
  carries how it was built.
- Do not release with failing tests or a failing docs lint. Report the failure instead.
- **A release that changes emitted output needs a note about existing trees.** Projects
  generated by the previous version keep the code it wrote; upgrading the package does not fix
  them. Say in `CHANGELOG.md` what to look for and whether a re-sync repairs it.

## If it went wrong

A published version cannot be replaced — yank it and publish a patch. Say in `CHANGELOG.md`
what was wrong so pinned consumers know why they must move, and whether they must regenerate.
