# partest-gen — parts of the generator

What the tool is made of and what each command produces. For the first run start at
[From an OpenAPI file to a collectable suite](howto-scaffold.md); for what you may edit afterwards, [The contract of generated code](concepts-generated-contract.md).

```bash
pip install partest-gen
```

`partest` comes with it — the generated suite runs on that harness, so the two are installed
together on purpose.

---

## 1. What it produces

From an OpenAPI document (plus an optional UI flag) a **runnable** pytest project that:

1. uses the `partest` harness through its public API — nothing vendored, nothing copied;
2. follows the coverage methodology: every operation is classified into a method subtype, and
   the stub set for that subtype is emitted with the correct `type=` on each call;
3. keeps API and UI suites in separate trees that do not share a session;
4. contains no product secrets, no role lists and no domain values.

The output is a set of **stubs with structure**, not finished tests. What "finished" means and
who owns which file: [The contract of generated code](concepts-generated-contract.md).

## 2. Pipeline

```text
OpenAPI document
   │  openapi_load.py      YAML/JSON, local path or URL
   ▼
SuiteIR                    ir.py — one OpIR per operation
   │                       method, path, tag, subtype, required_p1, params,
   │                       request_schema, success_response_schema, success_status
   ▼
emitters/                  resources.py drives the rest
   ▼
project tree               resources.py / skeleton.py write files, honouring the banner contract
```

The subtype and the required case list are **not decided here**. `ir.py` calls
`classify_endpoint` and `p1_test_cases` from `partest.methodology.api`, so a suite and its
generator always agree about what an endpoint is. Changing classification means changing
`partest`. The `api` in that path is an area, not a package layout detail: the harness release
this package requires splits its methodology into an API half and a UI half, and only the API
half is derived from a specification — which is the only half a generator reading OpenAPI can
use. The required version is in `CHANGELOG.md`.

## 3. Target tree

```text
{project}/
├── requirements/{base,api,ui,local}.txt
├── confpartest.py, conftest.py, env.example, pytest.ini
├── docs/{README.md, UI_GUIDE.md}
├── scripts/{run_ui.ps1, run_ui.sh}
├── .partest/{suite_ir.json, openapi_summary.md}
└── src/
    ├── api/
    │   ├── resources/{endpoints,payloads,validations,collections,rbac,security}
    │   └── tests/{conftest,test_zorro,<tag>/…}
    └── ui/                          # only with --with-ui / init-ui
        ├── conftest.py              # must not load OpenAPI — see [The generated UI layer](components-ui-layer.md)
        ├── pages/, components/, fixtures/, utils/, tools/
        ├── resources/ui_rbac_matrix.py
        ├── baselines/{reference,actual,diff}
        └── tests/{smoke,auth,rbac,visual}
```

## 4. Commands

```bash
# whole suite from a specification
partest-gen from-openapi ./my-suite --file openapi.yaml --depth p1 --with-ui

# empty skeleton, no specification yet
partest-gen init ./my-suite --name my-suite

# refresh generated artifacts after the specification changed
partest-gen sync-openapi ./my-suite --depth p1
# … and delete generated files whose operation is gone (otherwise only listed)
partest-gen sync-openapi ./my-suite --depth p1 --prune

# add the UI tree to an existing project
partest-gen init-ui ./my-suite

# inspect what the generator understood, without writing a project
partest-gen dump-ir openapi.yaml -o suite_ir.json

# star re-exports in the __init__.py files of a package you wrote by hand
partest-gen init-package-exports ./my-suite/src/my_helpers
```

`init-package-exports` is for packages you wrote by hand — say, your own helpers package. It
rewrites, whole and recursively, the `__init__.py` of every directory under the one you name
that holds modules: `from .module import *` lines under a banner of its own,
`# AUTO-GENERATED by partest.tools.generate_init — safe to re-run`. Commit first. Never run it
on a directory the generator writes, `src/api/resources` above all: that banner is not the
generator's, so the next `sync-openapi` keeps those files as yours (`endpoints/__init__.py`,
`collections/__init__.py`, …) and stops refreshing them. If that already happened, restore the
files from version control, or, without it:

```bash
# delete every __init__.py under src/api/resources whose first line is that banner, then
# sync with the --depth the project was generated with: it writes the generator's own
partest-gen sync-openapi ./my-suite --file openapi.yaml --depth <its depth>
# and the skeleton's (resources/, rbac/, security/): init writes only what is missing
partest-gen init ./my-suite
```

`sync-openapi` names only the files it would write; `init` without `--force` writes only what
is missing, so it restores the skeleton's `__init__.py` files and leaves everything else.

| `--depth` | Emits |
|---|---|
| `resources` | paths + collection facades |
| `default` | + payloads, validations, Default and NotAllowed tests |
| `p1` | + the full priority-one stub set per subtype, plus `P1_CHECKLIST.md` per tag |

| Flag | Meaning |
|---|---|
| `--entities a,b` | only these OpenAPI tags; the shared `paths.py`, collection facades and manager keep every tag already generated. A list matching no tag is refused |
| `--with-ui` | also emit the UI tree (orthogonal to `--depth`) |
| `--force` | overwrite files that do not carry the generated banner |
| `--prune` | `sync-openapi` only: delete generated files no operation of the specification produces any more; without it they are listed. Refused for a specification with no operations |
| `--version` | which generator produced a tree — the first thing to check on a bug report |

A specification that cannot be read stops every command that reads one (`init --openapi`,
`from-openapi`, `sync-openapi`, `dump-ir`) before anything is written: one line on stderr
naming the file and the problem, exit code 2, no traceback. That covers a missing file or a
directory, no read permission, text that is not UTF-8 (UTF-16 is named as such; a UTF-8 byte
order mark is fine), YAML or JSON that does not parse (with line and column), a top level that
is not a mapping, `info` or `paths` that holds a value but not a mapping (an empty one reads as
absent), and a `--url` that cannot be used:

- an HTTP error status — with the advice to download the file and pass it as a file;
- an HTML or XML page instead of a specification — told by the body, not the
  `Content-Type`; a login or error page, most often — with the same advice, as for a body that
  is empty or not a mapping;
- credentials in the URL that are not Latin-1, which requests cannot send — percent-encode
  them, or download the file;
- a rejected certificate — OpenSSL's reason (self-signed, expired, hostname mismatch) and how
  to get past it: `REQUESTS_CA_BUNDLE=/path/to/ca.pem`, or the file. `PARTEST_TLS_VERIFY` does
  not apply to the generator's download;
- anything else from `requests` or `urllib3` — the class of the failure and of its cause, such
  as `ConnectionError (NameResolutionError)` or `LocationParseError`, never the exception's
  text, which repeats the URL; when the server did answer (`TooManyRedirects`), with the
  advice to download the file;
- a body that cannot be decoded — UTF-16 the `Content-Type` does not announce, bytes outside
  the declared charset (named), a charset Python does not know — with the same advice.

An output that cannot be written is reported the same way: `dump-ir -o` to a directory, to a
path under a file, or where the system refuses the write prints
`error: cannot write IR to <path>: <reason>` and exits with code 2. The IR is written to a
temporary file beside the target and moved over it, so a failed write leaves the previous
file whole and no temporary file behind. A specification with a lone surrogate is refused
before anything is written, with `-o` or without; an IR that the encoding of stdout cannot
hold is one line with the advice to use `-o`.

After `init --openapi <URL>`, `from-openapi --url` or `sync-openapi --url`, a line starting with
`Not saved:` says that the download was not saved in the project while `docs/openapi.yaml`
is still the skeleton's `/health` placeholder, which the coverage report and a
`sync-openapi` without a source read. Such a `sync-openapi`, on a project with generated tags
the placeholder does not declare, prints a `Warning:` line naming them before it rewrites
`paths.py` — a warning, not a refusal. See [From an OpenAPI file to a collectable suite](howto-scaffold.md).

A downloaded document is decoded with the `charset=` its `Content-Type` declares, and as UTF-8
(a byte order mark accepted) when it declares none. A document without
an `openapi`/`swagger` field is read as before. Any other exception is a generator bug and is
raised as it is.

Only `http://` and `https://` sources are fetched, in any case and with surrounding
whitespace. Any string with `://` — whatever the scheme — is cleaned before it is shown or
stored as `SuiteIR.source` in `.partest/`; a string without `://`, a mistyped scheme such as
`http:/host/…` included, is a path and is printed as it is. Cleaning drops the query string
and the fragment, and turns credentials in the authority — the text up to the first `/`, `?`
or `#`, up to its last `@` — into `***@`. An `@` after the authority is ambiguous: a CDN path
(`cdn.jsdelivr.net/npm/@acme/spec@2/`) or the rest of a password with an unencoded `/`,
`?` or `#` (`admin:2024/q@host`, `tok/en@github.com`). **Ambiguous cases are hidden**: the
source is shown as `<URL not shown>` when the authority carries credentials and another `@`
follows anywhere — `u:p@registry.example/…/npm/@scope/…` included —, when an `@` follows the
authority and its host has a `:` (a port included) or is a name without a dot that is not an
IPv6 literal, and when the host after a userinfo `@` has a `:` not followed by a number. A
dotted host without a port and without credentials keeps its path visible. The cleaning never raises: if it failed, the source would be `<URL not shown>`
rather than a traceback with the raw text. A token inside the path itself cannot be told apart
and stays.

UI is orthogonal to depth. For a greenfield project `--depth p1 --with-ui` is the usual choice.
`--force` is not needed for a new directory: a file that is still exactly a skeleton
placeholder is replaced by the generated module either way, so `init` followed by
`from-openapi` or `sync-openapi` gives the same tree.

## 5. Emitters

| Emitter | Output |
|---|---|
| `paths` | `src/api/resources/endpoints/paths.py` — path constants per tag, deprecated operations included |
| `collections` | `collection_<tag>.py`, manager, factory. A deprecated operation keeps its entry in the facade's `paths`, and gets no payload, validation or test |
| `payloads` | `payloads/<tag>/*_payload.py` — shape-correct request bodies |
| `validations` | `validations/<tag>/*_validation.py` — response models |
| `tests_default` | Default and NotAllowed cases. NotAllowed probes only paths with a live operation of the tag, and never a method the specification declares on that path — under any tag, deprecated or not, whatever `--entities` selected |
| `tests_p1` | the subtype's priority-one set: permissions, new/update object, incorrect body, elements, … |
| `ui_layout` | the whole `src/ui` tree, scripts and the UI guide |

No emitter touches the filesystem on its own. They return `path -> source`;
`resources.py` collects that into one plan and writes it, applying the overwrite policy, and
`skeleton.py` does the same for the skeleton and the UI tree. Every write — these, `.partest/*`,
the copy of the specification — is refused when a symlink or junction lies on its path or it
resolves outside the project, and the command lists it. Text from the specification (paths,
`operationId`s, summaries, property and parameter names) is escaped wherever it lands in code,
invisible characters included; a property name that cannot be a field as it is (not an
identifier, a keyword, a name the module uses, `_private`, `model_*`) becomes `field_<snake>`
with an alias, and a tag or path that is a Python keyword gets a trailing `_`. A specification
that cannot be written at all — a lone surrogate, or on Windows a tag named like a device —
is refused before the first write. The same plan, taken for every tag at the deepest depth with
deprecated operations included, is what `sync-openapi` compares the tree against to find
orphans.

### Python API

Exported from `partest_gen.emitters` — the same calls `sync-openapi` makes:

| Call | Does |
|---|---|
| `emit_resources(project_root, suite, *, force=False, tags_filter=None, write_ir=True, depth="default") -> WriteResult` | writes the plan; `result.created`, `.skipped`, `.refused` (a link on the way). `ValueError` when `tags_filter` matches no tag |
| `find_orphans(project_root, suite, *, tags_filter=None, links=None) -> list[str]` | generated files no operation produces any more, project-relative. Pass a list as `links` to receive the links it did not enter |
| `remove_orphans(project_root, orphans, *, failed=None, skipped=None) -> list[str]` | deletes them after checking each again; returns what was deleted, puts paths that failed the re-check into `skipped` and those the system refused into `failed` |

`partest_gen.skeleton.init_skeleton(target, *, name, with_ui, force, openapi_source, suite_ir)`
writes the skeleton alone. `openapi_source` goes into `confpartest.swagger_files`, the
source of the coverage report: an `http://` or `https://` address as `"url"`, anything else as
a `"local"` path, `docs/openapi.yaml` by default. It is written as given, as an ASCII Python
literal with `\u`/`\U` escapes (the project name too), into a file projects commit — pass an address without credentials and without tokens
in its query.

`suite` is what `partest_gen.openapi_load.load_openapi(path_or_url)` returns. What it raises
when it cannot:

- `FileNotFoundError` or `OSError` for a file it cannot open;
- `ValueError` for a local file it cannot decode (`UnicodeDecodeError`) or parse
  (`json.JSONDecodeError`), and `partest_gen.openapi_load.SpecReadError` — a
  `ValueError` subclass, so `except ValueError` keeps catching it — for a shape it cannot
  build from, an HTML or XML page, a downloaded body it cannot decode, and credentials it
  cannot send. Its `downloaded` attribute is true when the source is a URL, and `stage` says
  where it failed (`fetch`, `read`, `shape`);
- for a downloaded body that parses as neither JSON nor YAML, `yaml.YAMLError` — **not** a
  `ValueError`. A value YAML parses but cannot build — an unquoted date that does not exist,
  such as `2023-02-29`, or a value its explicit tag cannot hold, such as `!!int abc` or
  `!!timestamp abc` — is a `yaml.constructor.ConstructorError` at the value's position, not
  the bare `ValueError` or `AttributeError` of the safe constructor. Its message shows the
  value cut to 40 characters and the reason only up to its first colon;
- the exceptions of `requests` and `urllib3` for a URL it cannot fetch — their text repeats
  the URL as given.

The parse error depends on the order the parsers are tried in. A local file is read as YAML
first and, when that fails, as JSON, so a file that is neither raises the JSON error
(`json.JSONDecodeError`), with the `yaml.YAMLError` that describes the file in its
`__context__` chain; a `.json` file is read as JSON only. A downloaded body is tried the other
way round — JSON, then YAML — so it raises `yaml.YAMLError`. The command line reports both as
"is not valid YAML", and a `.json` file as "is not valid JSON", with the line and column. `SuiteIR.source` holds the cleaned source
described above, also when the suite comes from `build_ir_from_openapi_dict(data, source=...)`.

## 6. Artifacts to read after a run

| File | Why |
|---|---|
| `.partest/openapi_summary.md` | operations × subtype × required cases — the map of the work |
| `.partest/suite_ir.json` | the same, machine-readable, if you script on top |
| `src/api/tests/<tag>/P1_CHECKLIST.md` | per tag, every required case and its stub file; rewritten on every sync, so progress is read from the coverage report (`missing_p1`) |

## 7. Limits worth knowing

- **Classification is heuristic.** Unusual paths get a plausible subtype, not a certain one.
  Check the summary before trusting the stub set; `partest` accepts explicit per-route
  overrides for the cases the heuristic cannot get right.
- **Payloads are shape-correct, not domain-correct.** Required business values are yours.
- **`sync-openapi` refreshes generated files only.** Hand-written tests that referenced a
  removed operation will not be fixed for you — see [Re-syncing after the specification changed](howto-resync.md). Generated files of a
  removed operation are listed after the sync and deleted only with `--prune`.
- **OpenAPI `webhooks` and `callbacks` are not emitted.** They are skipped silently today.
