# Разработка генератора

Как менять `partest-gen`, не ломая чужие репозитории. Границы и красные линии — `AGENTS.md`,
эта страница про механику.

## Установка для разработки

```bash
python -m venv .venv && . .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
python -m pytest tests/ -q
```

`partest` подтянется как зависимость. Если правишь оба пакета одновременно — ставь и его
редактируемым из соседнего чекаута, иначе будешь отлаживать релизную версию:

```bash
pip install -e ../partest_client
```

## Одна команда перед коммитом

```bash
python tools/check_all.py
```

Это тесты, линтер доков, индекс и проверка дрейфа `docs/wiki` ↔ `partest_gen/docs`. То же
самое гоняет CI, поэтому «у меня локально зелено» и «зелено на PR» — про один и тот же набор.
Перед релизом добавляется `--strict-docs` и `--package`; см. [[howto/release]].

## Инварианты, которые нельзя нарушить молча

1. **Баннер.** Файл, который генератор считает своим, начинается с
   `AUTO-GENERATED by partest-gen`. Расширение списка перезаписываемых файлов — потеря данных
   в чужом репозитории. Правило и его следствия: [[concepts/generated-contract]].
2. **Методология не форкается.** Подтипы, матрица P1 и классификатор берутся из
   `partest.methodology`. Локальная таблица «на время» переживёт любой срок —
   [[decisions/methodology-upstream]].
3. **Только публичный `partest.*` в эмитируемом коде.** Приватное имя в шаблоне превращается
   в поломку у консьюмера при обновлении харнесса.
4. **`type=` в каждом эмитируемом вызове.** Явно, даже там, где сработала бы инференция.
5. **UI-дерево не грузит API-сессию.** Ни `confpartest`, ни OpenAPI в `src/ui/conftest.py`.
6. **Ни домена, ни приватных путей в шаблонах.** Ни ролей, ни URL стендов, ни абсолютных
   путей — включая примеры в docstring.

## Где что лежит

| Файл | Отвечает за |
|---|---|
| `partest_gen/cli.py` | разбор аргументов и последовательность команд |
| `partest_gen/openapi_load.py` | чтение спеки: файл или URL, YAML или JSON |
| `partest_gen/ir.py` | спека → `SuiteIR`; здесь же вызов классификатора из `partest` |
| `partest_gen/skeleton.py` | дерево проекта, корневые файлы, запись на диск и политика перезаписи |
| `partest_gen/emitters/*` | по эмиттеру на артефакт; ни один не пишет на диск сам |
| `partest_gen/ui_layout.py` | всё `src/ui` целиком |
| `partest_gen/models_*.py` | легаси до IR; новый код туда не добавляем |

Почти весь объём `skeleton.py` и `ui_layout.py` — это текст шаблонов в строках. Идея вынести
их в файлы записана в [[status]]; до тех пор новые шаблоны кладём рядом, тем же способом.

## Как менять то, что генерируется

Порядок, а не набор:

1. Правишь эмиттер.
2. Правишь `tests/test_golden_suite.py` — он генерирует дерево из фикстурной спеки и
   собирает его `--collect-only`. Если изменение не видно в golden-тесте, оно не проверено.
3. Обновляешь страницу в `components/` и `verified:` на ней.
4. Строка в `CHANGELOG.md`.
5. Скилл `partest-scaffold`, если изменилась команда или контракт.

Проверка «а что реально получилось» — руками, один раз, на настоящей спеке:

```bash
partest-gen from-openapi /tmp/check --file tests/fixtures/sample_openapi.yaml --depth p1 --with-ui --force
cd /tmp/check && python -m pytest src/api/tests --collect-only -q
```

## Тесты

| Файл | Что держит |
|---|---|
| `tests/test_g1_skeleton.py` | дерево, корневые файлы, IR, `dump-ir` |
| `tests/test_g2_resources.py` | paths и коллекции, `sync-openapi` |
| `tests/test_g3_payloads.py` | payloads, validations, Default/NotAllowed |
| `tests/test_g4_p1_stubs.py` | набор P1-заглушек и чек-листы |
| `tests/test_g5_ui_layout.py` | UI-дерево и его изоляция |
| `tests/test_golden_suite.py` | e2e: спека → дерево → импорт и сбор |
| `tests/test_cli.py` | команды CLI и `--version` |
| `tests/test_docs.py` | линтер доков внутри pytest, состав колеса |

Новая возможность без теста в этом списке — незакрытая возможность.
