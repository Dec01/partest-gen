# Release checklist

Version-agnostic procedure. What is in the current release and what is planned lives in
[[status]]; product notes live in `CHANGELOG.md`.

Artifacts go to **PyPI**, the source and its history to **GitHub** — see
[[decisions/separate-package]].

## 1. Decide the number

Only bump on an explicit release request. Semver as practiced here — and note that for a code
generator, "public API" means **what it writes**, not only what it exports:

| Change | Bump |
|---|---|
| new emitter, new CLI flag, new `--depth`, richer stub | minor |
| bug fix, doc-only, internal refactor of an emitter | patch |
| a generated file changes name or moves | **major** |
| the overwrite policy widens in any way | **major** |
| the required `partest` floor rises | minor at least; major if the harness API changed under it |

The middle two are the ones that get misjudged. A renamed generated module breaks every
hand-written import in every project that ran the previous version — from the consumer's seat
that is indistinguishable from a removed function.

## 2. Prepare

```bash
python tools/docs_build_wheel.py            # regenerate partest_gen/docs from the wiki
python tools/check_all.py --strict-docs     # tests, docs lint, index, wheel drift
```

- [ ] `__version__` in `partest_gen/__init__.py` bumped — the only place; `setup.py` reads it
- [ ] `CHANGELOG.md`: `Unreleased` folded into the new version section
- [ ] `docs/wiki/status.md`: current version, what is next, the `partest` floor
- [ ] pages touched by the change have a fresh `verified:` date
- [ ] `install_requires` pins the `partest` floor the emitted code actually needs — a suite
      generated by this release must run on it
- [ ] no secrets, stand URLs, absolute local paths, or consumer project names anywhere in the
      package or in a page with `ships_in_wheel: true` — the linter checks, read the diff too

## 3. Look at what it generates, not only at what it exports

```bash
python -m pytest tests/test_golden_suite.py -q
```

The golden test generates a suite from the fixture specification and collects it. For a
release, also read the diff of what it produced if any emitter changed:

```bash
partest-gen from-openapi /tmp/rel-check --file tests/fixtures/sample_openapi.yaml \
  --depth p1 --with-ui --force
grep -rL "AUTO-GENERATED by partest-gen" /tmp/rel-check/src --include="*.py"
```

The second command lists files the generator does **not** claim. Anything unexpected there is
a banner that went missing — a file that will silently stop being refreshed in every project.

## 4. Build and inspect the artifact

```bash
python -m pip install -U build twine
python tools/check_all.py --package
python -m zipfile -l dist/partest_gen-*.whl | grep "partest_gen/docs"
```

The wheel must contain exactly the pages marked `ships_in_wheel: true` — no status page and
no ADRs. The sdist carries `partest_gen/**`, `CHANGELOG.md`, `LICENSE` and the packaging
files, nothing else. `MANIFEST.in` prunes `tests/`, `docs/`, `tools/`, `.claude/` and
`.github/`; if you add a top-level directory, decide there whether it ships before the next
release decides for you.

## 5. Publish

Publishing runs on GitHub with **trusted publishing**: PyPI authenticates the workflow by its
identity over OIDC. No API token exists — nothing to store, leak or rotate.

```bash
git push origin master
git tag -a vX.Y.Z -m "partest-gen X.Y.Z — one line on what it is"
git push origin vX.Y.Z
```

The tag starts `release.yml`. It re-runs every check with `--strict-docs`, refuses to continue
if the tag and `__version__` disagree, skips the upload if that version is already on PyPI,
and otherwise **waits for a review on the `pypi` environment**. That review is the approval:
nothing reaches PyPI until a human clicks it.

Verify afterwards from a clean environment:

```bash
python -m venv /tmp/verify && /tmp/verify/bin/pip install -U partest-gen
/tmp/verify/bin/partest-gen --version
/tmp/verify/bin/python -m partest_gen.docs list
/tmp/verify/bin/partest-gen from-openapi /tmp/verify-suite --file tests/fixtures/sample_openapi.yaml --depth p1
```

- [ ] version visible with `pip index versions partest-gen`
- [ ] the CLI runs from a fresh install and produces a collectable tree
- [ ] PyPI project page renders (`twine check` passing is necessary, not sufficient — open it)

### If you have to publish by hand

Only when the workflow is unavailable. Credentials belong in your own keyring or `~/.pypirc`,
never on a command line and never in a message:

```bash
python tools/check_all.py --strict-docs --package
python -m twine upload dist/*
```

- [ ] append a line to [[log]]
- [ ] update [[status]]: current version, and move closed items out of "what is next"
- [ ] if the release needed notable operational steps, fold them into this checklist

## 7. Rollback

PyPI does not allow re-uploading a version. To undo, yank the release and publish a patch.
Consumers pinned to the bad version must move; say in `CHANGELOG.md` what was wrong so they
know why.

A generator has a second kind of rollback: projects already generated by the bad version keep
the code it wrote. If the defect is in emitted output, the patch notes must say what to look
for in an existing tree and whether a re-sync fixes it.
