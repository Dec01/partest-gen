# ADR: генератор — отдельный пакет, а не подпакет `partest`

**Дата:** 2026-09-06 · **Статус:** принято

## Контекст

Генератор жил как `partest.project_gen` и ехал в каждый `pip install partest`. К моменту
выделения это ~5 800 строк — заметная доля пакета, — из которых почти всё это текст шаблонов.

Что с этим было не так:

1. **Разные аудитории.** Харнесс нужен каждому тесту в каждом прогоне. Генератор нужен
   один раз при заведении проекта и потом изредка при смене спеки. Первое — библиотека,
   второе — инструмент разработчика, и они не обязаны обновляться вместе.
2. **Разный темп и разная цена ошибки.** Баг в харнессе виден на первом же прогоне. Баг в
   эмиттере остаётся в чужом репозитории в виде записанных на диск файлов и переживает
   откат версии — обновлением его не отменить.
3. **Разное понимание semver.** Публичный контракт харнесса — экспортируемые имена.
   Публичный контракт генератора — **имена и расположение файлов, которые он пишет**.
   Переименование сгенерированного модуля ломает импорты в чужих ручных тестах так же, как
   удаление функции, но в одном пакете это правило пришлось бы держать в голове.
4. **Зависимости.** Генератору не нужны `matplotlib`, `httpx`, `playwright`; харнессу не
   нужен `pyyaml` ради парсинга спеки в момент скаффолда.

## Решение

Два дистрибутива:

| | `partest` | `partest-gen` |
|---|---|---|
| Что это | харнесс: клиент, покрытие, отчёты, UI | инструмент: спека → дерево проекта |
| Когда работает | в каждом прогоне тестов | при заведении проекта и при смене спеки |
| Публичный контракт | экспортируемые имена | имена и расположение эмитируемых файлов |
| Зависит от | — | `partest` |

Зависимость односторонняя и такой останется: генератор читает методологию харнесса, харнесс
о генераторе ничего не знает. Обратная зависимость сделала бы цикл и вернула бы ровно ту
связанность, ради снятия которой всё делалось.

## Что сделано для тех, кто уже поставил `partest`

- `partest.project_gen` остался как мост: импорт продолжает работать, если установлен
  `partest-gen`, и падает с внятным сообщением, если нет.
- Экстра `partest[gen]` ставит оба пакета одной командой.
- Мост объявлен устаревшим и снимается в мажорной версии `partest`, не раньше.

Команда `partest-gen` переехала целиком: её объявляет тот дистрибутив, который её реализует.
Это единственное, что ломается сразу — `pip install partest` больше не даёт CLI. Иначе два
пакета объявляли бы одну и ту же команду, и какая из них окажется в `PATH`, зависело бы от
порядка установки.

## Последствия

**Хорошие.** Пакет харнесса меньше и без шаблонов. Релизы независимы: правка эмиттера не
двигает версию библиотеки, которую тянут все прогоны. Правило «переименовал сгенерированный
файл — это мажор» теперь про весь репозиторий, а не про его часть.

**Цена.** Два репозитория, два CI, два релизных цикла, два комплекта доков. Совместимость
надо держать явно: нижняя граница `partest` в `install_requires` и строка в `status.md`.
При правке обоих пакетов сразу нужен `pip install -e` на оба чекаута.

**Что осталось общим.** Схема документации, инструменты в `tools/`, красные линии из
`AGENTS.md`. Расхождения допустимы, но должны быть названы здесь.

## Альтернативы

- **Оставить как было.** Дёшево сегодня, но ни одна из четырёх причин не исчезает; каждая
  следующая волна эмиттеров делает пакет тяжелее для тех, кто генератором не пользуется.
- **Экстра `partest[gen]` без отдельного дистрибутива.** Не решает главного: код всё равно
  в одном репозитории, с одной версией и одним понятием semver.
- **Вендорить генератор в шаблон проекта.** Каждый сгенерированный репозиторий получает
  форк генератора, который никто никогда не обновит.
