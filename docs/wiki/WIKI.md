# WIKI.md — схема документации partest-gen

Файл описывает, **как устроена** документация. Знаний о генераторе здесь нет.
Читается один раз перед правкой доков; в обычной работе не нужен.

Схема намеренно совпадает со схемой в репозитории `partest`: два пакета сопровождаются
одним человеком и одними агентами, и переучиваться при переходе между репозиториями —
лишняя работа. Расхождения допустимы только там, где они обоснованы, и должны быть
названы в [[decisions/separate-package]].

## Три слоя

| Слой | Где | Кто владеет | Правило |
|---|---|---|---|
| **Raw** — неизменяемые источники | вне репозитория | человек | снапшоты источников хранятся рядом с репозиторием, а не в нём |
| **Wiki** — производное знание | `docs/wiki/` | агент | создаёт страницы, обновляет, чинит перекрёстные ссылки |
| **Схема** — конвенции | этот файл + `AGENTS.md` | человек + агент | эволюционирует медленно, правится осознанно |

## Структура wiki

```text
docs/wiki/
  WIKI.md        схема (этот файл)
  index.md       каталог: одна строка на страницу — точка входа для агента
  log.md         хронология операций ingest / update / lint
  status.md      ЕДИНСТВЕННЫЙ источник статусов, версий, волн, «что дальше»
  concepts/      контракт генерируемого кода: почему именно так
  components/    части генератора: CLI, IR, эмиттеры, UI-слой
  howto/         рецепты: сгенерировать, пересинхронизировать, довести до зелёного
  decisions/     ADR: решение, контекст, последствия, дата
```

Выбор категории: `concepts` — «почему», `components` — «что есть», `howto` — «как сделать»,
`decisions` — «почему именно так, а не иначе».

## Frontmatter — обязателен на каждой странице

```yaml
---
title: partest-gen — parts of the generator
status: current            # current | draft | stale | archived
verified: 2026-09-06       # дата последней сверки с кодом
sources: [partest_gen/cli.py]   # файлы кода, от которых зависит страница
audience: agent            # user | maintainer | agent
ships_in_wheel: false      # true → страница уезжает в PyPI-колесо
---
```

`sources` — центральный механизм. `tools/docs_lint.py` сравнивает дату последнего коммита,
затронувшего файлы из `sources`, с `verified`. Если код новее — страница помечается **stale**.
Так документация не гниёт молча, а сама сообщает о расхождении.

Правило: если страница описывает поведение кода — у неё **должен** быть непустой `sources`.
Страницы `decisions/`, `howto/release` и служебные могут иметь пустой `sources`.

## Язык

Страницы с `ships_in_wheel: true` — **английский**: их читает любой пользователь пакета.
Внутренние страницы (`status`, `log`, `decisions/`, `howto/contribute`) — русский: их читает
сопровождающий. Смешивать в пределах одной страницы нельзя.

## Ссылки

- Внутри wiki: `[[howto/scaffold]]` — путь от `docs/wiki/` без расширения.
- На код: обычная markdown-ссылка на путь от корня репозитория, при желании с `:строкой`.
- Наружу: только публичные URL. Приватные пути (`C:\…`, UNC, URL стендов) запрещены везде,
  в страницах с `ships_in_wheel: true` это ошибка линтера.
- **Страница, уезжающая в колесо, может ссылаться только на такие же страницы.** Иначе в
  колесе останется висящий заголовок внутреннего документа — линтер это ловит.
- Ссылка на wiki `partest` — только как публичный URL. Двойные квадратные скобки работают
  внутри одного репозитория; в соседний они не ведут.

## Версии

Единственный источник версии — `partest_gen/__init__.py` (`__version__`); `setup.py` читает его.
Литерал версии допустим только в `status.md`, `CHANGELOG.md` и `docs/PYPI.md`.
В остальных страницах пишем «текущий релиз — см. [[status]]».

Версия `partest`, от которой зависит генератор, — литерал в `setup.py` и строка в `status.md`.
В прозе wiki её не дублируем.

## Рабочие циклы

**Ingest** — появился новый источник (запрос от консьюмера, разбор инцидента, чужая спека):
положить в локальный `docs/raw/<источник>/<дата>/` (в `.gitignore`), разнести выводы по
страницам wiki, добавить строку в `log.md`. Источник не редактируем и **не публикуем**.

**Query** — вопрос: `index.md` → 1–2 страницы. Если ответа не нашлось, но он был получен из
кода — завести страницу, чтобы следующий раз обошёлся без раскопок.

**Lint** — `python tools/docs_lint.py`: битые ссылки, протухшие `verified`, литералы версий,
приватные пути, дрейф `docs/wiki` ↔ `partest_gen/docs`. Запускается и внутри
`pytest tests/test_docs.py`.

## RAG — когда включать

Сейчас RAG **не используется**: корпус мал, `index.md` + grep точнее и дешевле эмбеддингов.
`tools/docs_index.py` уже собирает машинный `index.json` — то есть корпус подготовлен.
Критерии включения те же, что в `partest`: wiki > ~60 страниц или > ~15 000 строк, либо
появляется сопоставление «код ↔ документы аналитики».

Отдельная оговорка для этого репозитория: два пакета — два корпуса. Если RAG включается,
он индексирует оба, иначе ответ «где это лежит» будет систематически неполным.

## Инварианты правки

1. Ни один файл не удаляется молча: либо `git mv`, либо запись в `log.md` с преемником.
2. Один факт живёт в одном месте; остальные ссылаются на него.
3. Статус, версия, «что дальше» — только в `status.md`.
4. Меняешь то, что генерируется, — обновляешь: `components/`, `CHANGELOG.md`, скилл
   `partest-scaffold`, golden-тест.
5. Каждая заметная правка — строка в `log.md` (дата, что сделано, какие страницы затронуты).
